Structuring Production-Grade Terraform Modules for Highly Available AWS Architectures

By Vivek Sabhanayakam

When managing Infrastructure as Code for multi-region AWS footprints, monolithic Terraform configurations eventually become risky. Duplication grows, blast radius increases, and state management becomes fragile.

To build resilient and highly available AWS architectures, infrastructure must be organized into reusable and isolated modules.

1. The Anti-Pattern vs. Enterprise Standard

Monolithic layout (anti-pattern)

Placing VPC, security groups, compute, and EKS resources inside one large main.tf file makes routine changes dangerous and difficult to review safely.

Modular layout (enterprise standard)

Separate foundational domains like networking, IAM, compute, and database into distinct modules with clear state and ownership boundaries.

2. Production Module Directory Structure

my-infrastructure-repo/
│
├── modules/
│   ├── vpc/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── eks/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│
└── environments/
    ├── dev/
    │   ├── main.tf
    │   └── backend.tf
    └── prod/
        ├── main.tf
        └── backend.tf

This separation keeps environments consistent while isolating state lifecycle by stage.

3. Hardening Module Security & Reliability

Rule A: Never hardcode variables

Use variable validation to prevent invalid input from reaching critical resources.

variable "vpc_cidr" {
  type        = string
  description = "The foundational CIDR block for the AWS VPC"
  validation {
    condition     = can(cidrnetmask(var.vpc_cidr))
    error_message = "The vpc_cidr value must be a valid CIDR block notation."
  }
}

Rule B: Enforce remote state locking

Never keep production state locally. Use remote state with concurrency locking.

terraform {
  backend "s3" {
    bucket         = "enterprise-tf-state-storage"
    key            = "production/network/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "terraform-state-locks"
    encrypt        = true
  }
}

4. Designing for High Availability

Distribute resources across multiple AZs programmatically rather than hardcoding single-zone assumptions.

data "aws_availability_zones" "available" {
  state = "available"
}

Use AZ data sources in subnet definitions to preserve resilience during single data-center failures.

Summary for Platform Engineers

Moving from ad-hoc Terraform scripts to isolated, versioned modules is a major maturity leap for platform teams. Focus on reducing blast radius, isolating environments, and treating infrastructure changes with the same engineering discipline as application releases.
